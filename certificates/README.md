- **Far region.** The `.boxes.jsonl.gz` file is the certificate: one JSON line per leaf (accepted with its multipliers, discarded with its symmetry pair, or handed to the local lemma). The `.json` file next to it holds the counts and the parameters ($\bar S$, $T$ or $T_1$, denominators); replay reads both. Replay: `python -X utf8 tests/replay_all.py`.
- **Local region.** The local stage stores no box record; **re-running the tool is the check** (docs/verification.md §3). The `*_local.json` files are only the summaries of the original runs (faces, boxes evaluated and accepted, candidates used). Some keys inside `"info"` are in Japanese because the original runs used the code before its comments and messages were translated; the translated code writes the same numbers under English keys.
- `d16d_cubinoct_far.json` is not part of the cubinoct proof (which uses `d16_cover_*`). It is kept because the Lean module `PackLean.D16.CubOct.Data` (constants of the piece, container, symmetry pairs and the upper bound for cubinoct) was exported with `d16d_*` and takes $\bar S$ and $T$ from it.
- The cubintet tool also reads `verifier/d28_cubintet_beta.json` ($\beta = 11/49$, chosen by stage 0); it sits next to `d28_common.py`, which loads it.
- **Stored local certificates (v0.2.0).** For `cubinico_n02` and `octintet_n02` the local leaves are stored and re-checked from the record (`d30_local.py --verify`, `d31_local.py replay J|C`; both are run by `tests/replay_all.py`). `d30_cubinico_claim_nolp.json` is the output of `d30_claim.py`, which combines the local verify, the far coverage check and the far replay. Some keys and values inside `"info"`, the `"reason"` of a stopped run and the `"note"` of the claim file are Japanese, because they are written by the code; the translated code writes the same strings (as `\u` escapes in the source) so that re-generated records stay identical.
- **Stored local certificates (v0.3.0).** `d30_s3_octinico_local.json` is re-checked by `d30_s3_local.py verify`, and `d30_s3_octinico_claim.json` is the output of `d30_s3_claim.py` (local verify, far coverage and replay, equal tube constants). The claim file also compares the SHA-256 of the code that made the records with the current files; the records were made with the original (Japanese-commented) code, so with the translated `verifier/` all six are reported as different. This comparison is informational only: acceptance is re-decided by the current code, and the claim passes. Japanese strings inside `"info"`, `"tube_identity"` and the claim's `"note"` are written by the code, as for cubinico. `d40_local.leaves.jsonl.gz` is re-checked by `d40_local.py replay`; `d40_tests.py --only chain` runs local replay, far replay and the upper-bound check together. Some keys of `d40_upper.json` are Japanese (written by the code).
- **tetintet_n05 (v0.3.0).** The records were made with $R_0=1/16$, which `d37_tet_n05_common` reads from the environment variable `D37_R0` (default 1/32); `d37_tet_n05_replay_both.py --r0 1/16` sets it and replays both records and the upper bound.
- **dodintet (v0.3.0).** The far record is the union of the main part and the continuation: the original run ended with two unfinished regions around the optimum, whose rows were removed by hand and redone after a fix of the pruning heuristic (`d45_dodintet_far.py run --part 1`). The claim rests only on the replay of the union (5,477 boxes). `d45_dodintet_far_run1.json` is the summary of the main run and says `closed: false`; this is expected. `dodintet_n02.json` is a byte-identical copy of the public numerical record of the configuration; `d45_dodintet_upper.py` reads it only to re-derive $\hat q$ and compare it with `d45_dodintet_upper.json` (the claim and Lean use the stored $\hat q$). The `note` of `d45_dodintet_upper.json` is Japanese (written by the code).
- **dodincub, dodinoct (v0.3.0).** Same record types as cubinico, made with `d30x_problems.py` in front of the d30 tools
  (`python -X utf8 verifier/d30x_problems.py verifier/d30_claim.py dodincub d30x_dodincub_local_r16.json d30_dodincub_far`).
  The dodincub local record was run with LP allowed, but every accepted leaf is a single candidate (`"lp": {"accepted": 0}`).
  For dodinoct, $\rho_0=1/16$ with single candidates does not close; the claim uses $\rho_0=1/32$ for both the local and the
  far record (hence `_r32`). `params.sha256` in the local records is the SHA-256 of the original (Japanese-commented) code;
  it is written only, not compared, and re-running the translated code gives identical records apart from these values and
  the run times. Japanese keys inside `"info"` and the claim's `"note"` are written by the code, as for cubinico.
- **Exact configurations (v0.2.0).** `plateau_<solid>_n<N>.json` hold, for each piece, the exact coordinates of its vertices as pairs $[a,b]$ meaning $a+b\sqrt d$ ($d=5$ for icosahedra, $d=2$ for octahedra), with $a,b$ as strings `"p/q"` (no floating point), and the container constant $c$. They were obtained by rounding public numerical records (whose ids and floating-point sizes are kept as reference strings) and are the only input of the substitution checks; for octintet $n=2$ the configuration is the one of test U (both pieces with $R=I$).
